## Claude Code

- **Skills.** Personal skills live at `~/.claude/skills/<skill-name>/SKILL.md`; project skills at `.claude/skills/`; enterprise from the managed settings directory (Linux example `/etc/claude-code/.claude/skills/`). Source: https://code.claude.com/docs/en/skills (Locations table).
  - Precedence on name collision: "Enterprise over personal, personal over project" (same page, Precedence table).
  - Symlinks: "A `<skill-name>` entry in the enterprise, personal, or project location can be a symlink to a directory elsewhere on disk. Claude Code reads `SKILL.md` from the target and loads the skill once even if several locations point at the same target." (same page, Symlinks.) That page does not say anything about a symlinked *file* `SKILL.md`, nor a symlinked `skills/` root.
  - Live reload: "Claude Code watches skill directories for file changes… picks up the change within the current session, without a restart." A top-level skills directory that did not exist at session start is not watched; `/reload-skills` is needed. Same page, Live change detection.
  - `~/.agents/skills` is not among the locations the page lists. The page was truncated at 100,000 of 118,114 characters, so this is "not documented in the part read", not proof of absence.
  - Machine check: `~/.claude/skills` on this Mac holds symlinks to `~/.skills-manager/skills/*` and to `~/.cua-driver/skills/cua-driver`, and they load.
- **Global agent instructions.** `~/.claude/CLAUDE.md` ("Personal preferences for all projects"). Windows: "`~/.claude` means `%USERPROFILE%\.claude`"; `CLAUDE_CONFIG_DIR` relocates it. Sources: https://code.claude.com/docs/en/memory (location table); https://code.claude.com/docs/en/settings (Windows note); https://code.claude.com/docs/en/claude-directory.
  - Load order: all discovered files are concatenated, not overridden; "instructions closer to where you launched Claude are read last". Managed-policy CLAUDE.md (macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`, Linux/WSL `/etc/claude-code/CLAUDE.md`, Windows `C:\Program Files\ClaudeCode\CLAUDE.md`) loads before user and project files. (memory page.)
  - `AGENTS.md` is read only as *project* instructions, and only when no `CLAUDE.md`/`CLAUDE.local.md` exists in or above the working directory; `~/.claude/CLAUDE.md` does not count for that check. v2.1.277+. (memory page, AGENTS.md section.) No user-level `AGENTS.md` location is documented.
  - Symlinks: `.claude/rules/` supports symlinks; a symlink to a network path (UNC `\\server\share`, `/net`, `/Network`) is not followed ("`\\wsl$` paths don't count as network paths"). In Cowork sessions only, a `~/.claude/CLAUDE.md` that is itself a symlink or hard link is skipped. (memory page.)
- **User-level MCP server definitions.** Scopes are local (default), project (`.mcp.json`), user. "Local" and "User" both live in `~/.claude.json`; local under `projects["<path>"].mcpServers`. (https://code.claude.com/docs/en/mcp, scope table.) Machine check (key names only): this Mac's `~/.claude.json` has a top-level `mcpServers` object, alongside account details, caches, and per-project state; so the file is mixed Claude-written state, not a definitions-only file.
  - Format: JSON `mcpServers.<name>` with `type` (`http`/`sse`/`ws`; a `url` entry with no `type` is read as stdio and skipped with an error), `command`/`args`/`env`, `url`/`headers`.
  - Precedence: local > project > user > plugin > claude.ai connectors; matched by name across the three scopes; "The entire server entry from that source is used; fields are not merged across scopes." A `managedMcpServers` managed setting ranks above all (v2.1.259+). (mcp page.)
  - `~/.claude/.mcp.json` and a `settings.json` `mcpServers` key are not described as definition sources in what the page says. The page says settings keys (`enabledMcpjsonServers`, etc.) only approve or toggle.
  - Reload: `list_changed` notifications refresh tools in a live session; `/mcp` → Reconnect. Whether hand-editing `~/.claude.json` or `.mcp.json` takes effect without a restart "isn't stated" on the page.
  - Backups: Claude Code copies `~/.claude.json` to `~/.claude/backups/` before rewriting; a file it cannot parse is moved aside and the user is asked to reset (https://code.claude.com/docs/en/settings, "Fix a broken settings file").
- **Auth state.** Login credentials: macOS Keychain, falling back to `~/.claude/.credentials.json` (mode 0600); Linux the same file; Windows `%USERPROFILE%\.claude\.credentials.json`. `CLAUDE_CONFIG_DIR` moves the file and keys the Keychain entry to that directory. (https://code.claude.com/docs/en/authentication, Credential management.) For MCP: "The client secret is stored securely in your system keychain (macOS) or a credentials file, not in your config"; `claude mcp logout <name>` clears; removing a server also deletes its tokens and client registration (mcp page). The exact file/key for MCP tokens is not documented in the pages read.
  - Machine check: `~/.claude/mcp-needs-auth-cache.json` exists (an unauthenticated-servers cache, not read).
- **Settings precedence (other config).** managed > command line > project local > shared project > user; edits to settings files reload without restart. (https://code.claude.com/docs/en/settings.)

## Codex (OpenAI Codex CLI)

Config home is `$CODEX_HOME`, default `~/.codex` (`find_codex_home`, `codex-rs/utils/home-dir/src/lib.rs`). `CODEX_HOME` must exist and is canonicalized. `codex-rs/config/src/codex_home_symlink.rs` and the key `allow_symlinked_codex_home` show that a symlinked `CODEX_HOME` is a gated case (referenced from `sandboxing/src/seatbelt.rs:449`: "set `allow_symlinked_codex_home = true` at the top level of `$CODEX_HOME/config.toml`"). The default home is built from `dirs::home_dir()` so on Windows it is `%USERPROFILE%\.codex` (inferred from code; the docs fetched don't state it).

- **Skills.** Source `codex-rs/ext/skills/src/host_roots.rs`: user scope roots are `$CODEX_HOME/skills` ("Deprecated user skills location… kept for backward compatibility") and `~/.agents/skills`; repo roots are `.agents/skills` in each directory from cwd up to the project root, plus project-layer `.codex/skills`; admin is the system layer's `skills` folder; system skills come from a cache dir. Docs (https://learn.chatgpt.com/docs/build-skills): repo `.agents/skills` walk, user `$HOME/.agents/skills`, admin `/etc/codex/skills`. Windows admin path: not documented.
  - Symlinks: docs: "Codex supports symlinked skill folders and follows the symlink target when scanning these locations." Source `ext/skills/src/loader/host.rs:165`: `User | Repo | Admin => DirectorySymlinkPolicy::Follow`, `System => Ignore`. A comment in `discovery.rs` mentions "file symlinks omitted by the walk" and falls back to a filesystem probe for `SKILL.md` metadata; handling of a symlinked `SKILL.md` *file* is not stated.
  - Duplicates: docs say Codex "doesn't merge" same-name skills; both can show in selectors. No precedence order stated.
  - Reload: docs: "Codex detects skill changes automatically. If an update doesn't appear, restart Codex." Edits to `~/.codex/config.toml` need a restart.
  - Limits seen in source: `MAX_SKILLS_ENTRIES_PER_ROOT = 20_000`; hidden directories pruned depending on mode.
- **Global agent instructions.** `$CODEX_HOME/AGENTS.override.md` is checked first, else `$CODEX_HOME/AGENTS.md`; only the first non-empty file counts at global scope (https://learn.chatgpt.com/docs/agent-configuration/agents-md). Constants `AGENTS.md` / `AGENTS.override.md` in `codex-rs/core/src/agents_md.rs:43-45`. Project chain: root → cwd, per-directory `AGENTS.override.md`, `AGENTS.md`, then `project_doc_fallback_filenames`; joined root-first so nearer files come later; combined cap `project_doc_max_bytes` (32 KiB default). Built once per session; "Restart Codex after editing".
- **User-level MCP server definitions.** `[mcp_servers.<name>]` tables in `~/.codex/config.toml` (shared by CLI, desktop app, IDE extension); also `.codex/config.toml` in trusted projects. Stdio keys: `command`, `args`, `env`, `env_vars`, `cwd`; HTTP keys: `url`, `auth` (`oauth` default | `chatgpt`), `bearer_token_env_var`, `http_headers`, `env_http_headers`, `http_headers_helper`; shared: `enabled`, `required`, `startup_timeout_sec`, `tool_timeout_sec`, `enabled_tools`, `disabled_tools`, `oauth.*`. (https://learn.chatgpt.com/docs/extend/mcp?surface=cli.) The page does not say whether a manual `config.toml` edit needs a restart; the desktop UI prompts "Restart".
  - Layer precedence (`codex-rs/config/src/loader/README.md`): highest → lowest: legacy managed (MDM, file), session flags (CLI), Project `.codex/config.toml`, User profile, User `config.toml`, enterprise cloud, System. System file: `/etc/codex/config.toml` (Unix), `%ProgramData%\OpenAI\Codex\config.toml` (Windows) (`loader/mod.rs`). Merge is key-wise TOML merge (`merge_toml_values`); a project-layer denylist keeps credential-routing keys like `openai_base_url` from project config (`loader/mod.rs`, `PROJECT_LOCAL_CONFIG_DENYLIST`).
  - Machine check: `~/.codex/config.toml` is mode 0600 and mixes `[mcp_servers.*]` with `[tui]` and `[projects."…"] trust_level`, so Codex also writes trust state into the same file as definitions.
- **Auth state.** `mcp_oauth_credentials_store` (`config/src/types.rs`, enum `OAuthCredentialsStoreMode`): `auto` (default; keyring, fall back to file), `file` (`$CODEX_HOME/.credentials.json`, "readable to Codex and other applications running as the same user"), `keyring` (fail if unavailable). On Linux the keyring is Secret Service over DBus (`rmcp-client/src/oauth.rs` header). `$CODEX_HOME/auth.json` holds the CLI's own login (a separate file; machine check: exists, mode 0600). `$CODEX_HOME/mcp-oauth-locks/` holds refresh locks (exists on this Mac).

## OpenCode

Global paths are built from XDG variables with a home-directory fallback and no per-OS branch: `config = $XDG_CONFIG_HOME || ~/.config`, `data = $XDG_DATA_HOME || ~/.local/share` (`packages/util/src/global-roots.ts`). So on Windows, absent `XDG_*` variables, the config dir is `%USERPROFILE%\.config\opencode` (code behavior; docs don't state it). The system-managed directory is per-OS: macOS `/Library/Application Support/opencode`, Linux `/etc/opencode`, Windows `%ProgramData%\opencode` (`packages/core/src/config/discovery.ts` and docs `config.mdx`).

- **Skills.** Docs (`packages/web/src/content/docs/skills.mdx`): project `.opencode/skills`, `.claude/skills`, `.agents/skills`; global `~/.config/opencode/skills`, `~/.claude/skills`, `~/.agents/skills`. Project paths are walked from cwd up to the git worktree. `OPENCODE_DISABLE_CLAUDE_CODE` / `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS` switch off the `.claude` ones (`rules.mdx`).
  - Symlinks: `packages/core/src/config/plugin/skill-scan.ts` does `fs.stat` on each symlink entry and treats it as the directory or file it points to; max depth 6; entries starting with `.` are skipped. A broken link becomes type `other` and is skipped.
  - Reload: `packages/core/src/config.ts` and `skill.ts` wire a filesystem `Watcher` and `reload`; user-facing statement of restart need: not found in docs read.
- **Global agent instructions.** `~/.config/opencode/AGENTS.md`; Claude fallback `~/.claude/CLAUDE.md` "used if no `~/.config/opencode/AGENTS.md` exists". Project: `AGENTS.md`, else `CLAUDE.md`, walking up. "The first matching file wins in each category." (`rules.mdx`.) Extra files via `instructions` in `opencode.json`.
- **User-level MCP server definitions.** `mcp.<name>` objects in `opencode.json`/`opencode.jsonc`: local `{type:"local", command:[…], environment, cwd, enabled, timeout}`; remote `{type:"remote", url, headers, oauth, enabled, timeout}` (`mcp-servers.mdx`; schema `packages/core/src/v1/config/mcp.ts`). Config precedence, later wins, files merged key-wise: remote org config → global `~/.config/opencode/opencode.json` → `OPENCODE_CONFIG` file → project `opencode.json` → `.opencode` dirs → `OPENCODE_CONFIG_CONTENT` → managed files → macOS MDM preferences (`config.mdx`, "Precedence order"). `{env:VAR}` and `{file:path}` substitution is supported in config values.
- **Auth state.** Docs (`mcp-servers.mdx`): tokens stored "in `~/.local/share/opencode/mcp-auth.json`"; `opencode mcp auth <name>` / logout manage them. A test in `packages/core/test/config/agent.test.ts` lists that same path as a denied read. Not verified against the v2 source at `df6fb9a46`: in that tree provider credentials moved to a database (`packages/core/src/credential.ts`, migration `…import_legacy_credentials`), and I found no non-test code referencing `mcp-auth.json`. Treat the path as docs-stated, not code-confirmed, for v2.

## Pi (the pi coding agent)

Agent directory `<agent-dir>` defaults to `~/.pi/agent` (`getAgentDir()` = `join(homedir(), ".pi", "agent")`, `src/config.ts:605-610`), overridable with `PI_CODING_AGENT_DIR`. Project config in `.pi/`, read "after project trust is granted". Source: `packages/coding-agent/docs/configuration.md`. Windows: same relative path under `os.homedir()` (code); the Windows doc page covers shells, not this directory.

- **Skills.** `<agent-dir>/skills/`, `.pi/skills/`, plus "the Agent Skills locations `~/.agents/skills/` and `.agents/skills/`" (project ones walked cwd → repo root). Recursive discovery. Name collisions: "keep the first discovered skill and produce a warning". (`docs/skills.md`.)
  - Symlinks: `src/core/skills.ts:202-244` — symlink entries are `statSync`-ed and followed (file or directory); broken links skipped; the loader dedupes by real path ("Skip silently if we've already loaded this exact file (via symlink)").
  - Reload: "Run `/reload` after editing a skill during an active session." (`docs/skills.md`.)
- **Global agent instructions.** `<agent-dir>/AGENTS.override.md`, `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`, or `CLAUDE.MD`, "applied across working directories". Also `<agent-dir>/SYSTEM.md` (replaces default prompt) and `APPEND_SYSTEM.md`. Context files are also loaded from the working directory and parents; `AGENTS.override.md` replaces only same-directory files. Context-file discovery does not require project trust. (`configuration.md`.) `/reload` after manual edits.
- **User-level MCP server definitions.** Built in at this version: `<agent-dir>/mcp.json` (`~/.pi/agent/mcp.json`) and project `.pi/mcp.json`; JSON `mcpServers`, stdio `command/args/env/cwd`, HTTP `url/headers/oauth`, SSE rejected. "A project entry replaces a user-level entry with the same name"; a project entry with no `command`/`url`/`type` overrides only `enabled`, `exposure`, `toolExposure`. `env`/`headers` values expand `${VAR}` and `!command`. (`docs/mcp.md`.) "Run `/reload` after adding, removing, or changing a server outside the session."
  - Machine check: this Mac has `~/.pi/agent/mcp.json` (one stdio server) and `~/.pi/agent/skills` (symlinks into `~/Developer/personal/skills`). Pi is not on `PATH` here, so the installed version is unknown; the config format matches the 1.4.0 docs.
- **Auth state.** MCP OAuth tokens: `~/.pi/agent/mcp-auth.json`, keyed by server name + URL; "Signing out deletes the stored credentials." (`docs/mcp.md`.) Model-provider keys/OAuth: `<agent-dir>/auth.json` (`configuration.md`). Both are separate from `mcp.json`.

## Gemini CLI

- **Skills.** Docs `docs/cli/skills.md`: precedence low → high: built-in, extension, user (`~/.gemini/skills/` or the `~/.agents/skills/` alias), workspace (`.gemini/skills/` or `.agents/skills/`). "Within the same tier… the `.agents/skills/` alias takes precedence over the `.gemini/skills/` directory." Reload: `/skills reload` (or `/skills refresh`) "to scan for new or modified skills without restarting the CLI" (`docs/cli/using-agent-skills.md`).
  - Loader (`packages/core/src/skills/skillLoader.ts:148-160`): `fs.stat` on the root, then `glob(['SKILL.md','*/SKILL.md'], {cwd, absolute, nodir:true, ignore:[node_modules,.git]})` — only one directory level; no `follow` option is passed. Docs do not mention symlinks. Whether `glob` descends a symlinked skill directory at that single `*` segment was not tested.
- **Global agent instructions.** `~/.gemini/GEMINI.md` ("Global context file"), then workspace and parent `GEMINI.md`, then JIT-discovered ones; all concatenated. `context.fileName` can add names such as `AGENTS.md`. `@file.md` imports. `/memory reload` re-scans. (`docs/cli/gemini-md.md`.) `GEMINI_CLI_HOME` relocates the base for the user `.gemini` folder (`docs/reference/configuration.md`).
- **User-level MCP server definitions.** `mcpServers` object in `~/.gemini/settings.json`; project `.gemini/settings.json`. Settings precedence low → high: defaults, system-defaults file, user, project, system settings file, environment variables, CLI args; "Workspace settings override user settings". System paths include `C:\ProgramData\gemini-cli\settings.json` on Windows. (`docs/reference/configuration.md`, `docs/cli/settings.md`, `docs/tools/mcp-server.md`.) Reload behavior for settings edits: not found in the pages read.
- **Auth state.** MCP OAuth tokens go to the OS keychain via `HybridTokenStorage`, with an encrypted-file fallback; the file path resolves to `mcp-oauth-tokens.json` under the global runtime dir (`~/.gemini`, or `~/.cache/.gemini` under macOS Seatbelt sandbox) (`packages/core/src/config/storage.ts:70-72,92-105`, `packages/core/src/mcp/oauth-token-storage.ts`). Env vars `GEMINI_FORCE_FILE_STORAGE` (`FORCE_FILE_STORAGE_ENV_VAR`) and a separate encrypted-file flag exist. Google login: `oauth_creds.json` (`storage.ts:22`). A definition in `settings.json` carries no tokens unless the user puts them in `headers`/`env`.

## GitHub Copilot CLI

Closed source; evidence is the docs plus the public changelog (`github.com/github/copilot-cli/changelog.md`).

- **Skills.** Personal: `~/.copilot/skills` or `~/.agents/skills`; project: `.github/skills`, `.claude/skills`, `.agents/skills` (https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-skills). `/skills reload` picks up mid-session additions. Precedence: not stated. Symlinks: docs silent; changelog 1.0.62 (2026-06-13): "Load skills from symlinked directories outside the configured root"; 1.0.68: "Avoid duplicate skill and command parse errors from symlinked scan roots". Changelog 1.0.66 (2026-06-30): "COPILOT_HOME and --config-dir stop loading skills from ~/.agents/skills" (meaning as worded; the interaction with the docs' personal-location list is not spelled out).
- **Global agent instructions.** `~/.copilot/copilot-instructions.md` ("User-level instructions that apply across repositories") and `~/.copilot/instructions/**/*.instructions.md`; `COPILOT_HOME` replaces `~/.copilot`. Repo: `.github/copilot-instructions.md`, `.github/instructions/**/*.instructions.md`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`; extra dirs via `COPILOT_CUSTOM_INSTRUCTIONS_DIRS`. "Does not define a general precedence order." Edits apply after restart/resume. (https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-custom-instructions.)
- **User-level MCP server definitions.** `~/.copilot/mcp-config.json`, top-level `mcpServers`; project `.mcp.json` (cwd → repo root) and `.github/mcp.json`; in one directory `.mcp.json` wins over `.github/mcp.json`; closer-to-cwd wins; project beats user; project servers load only after folder trust. `/mcp add` servers are live immediately; reload after hand edits: not described. (https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-mcp-servers.) Changelog 1.0.93: "Read user settings only from ~/.copilot/settings.json; user-setting keys in ~/.copilot/config.json are ignored", i.e. `config.json` also holds app state ("saved settings such as dismissed prompts, trusted folders and sign-ins", 1.0.9x entry near line 130).
- **Auth state.** Where MCP OAuth tokens are stored: not documented in the docs page or changelog lines read. The changelog confirms OAuth flows for MCP (CIMD support, token reuse), without naming a location.

## Cursor

Closed source; docs only.

- **Skills.** User-level "(global, local machine)": `~/.agents/skills/` and `~/.cursor/skills/`; compatibility dirs `~/.claude/skills/`, `~/.codex/skills/`, plus project `.agents/skills/`, `.cursor/skills/`, `.claude/skills/`, `.codex/skills/`. Recursive walk. Only `~/.cursor/skills/` syncs to Cloud Agents. Precedence, symlinks, Windows paths: not stated. (https://cursor.com/docs/skills.)
- **Global agent instructions.** No file-based user-level location is documented. "User Rules" are "global preferences defined in Customize → Rules"; storage location not stated. Order: "Team Rules → Project Rules → User Rules", earlier wins on conflict. Project `AGENTS.md` and `.cursor/rules` only. (https://cursor.com/docs/context/rules.)
- **User-level MCP server definitions.** `~/.cursor/mcp.json` (global) and `.cursor/mcp.json` (project); JSON `mcpServers`; stdio `command/args/env/envFile`; remote `url/headers/auth`; interpolation `${env:NAME}`, `${userHome}`, `${workspaceFolder}`. Precedence between the two files, hot reload, and OAuth token location: not stated; "update your local files and restart Cursor" for custom servers. Windows path: not stated beyond `${userHome}`. (https://cursor.com/docs/context/mcp.)

## Amp

Closed source; docs only.

- **Skills.** First skill with a given name wins, in this order: `~/.config/agents/skills/`, `~/.agents/skills/`, `~/.config/amp/skills/`, project `.agents/skills/` (and parents), project `.claude/skills/`, `~/.claude/skills/`, `~/.claude/plugins/cache/`, `amp.skills.path`, personal repo, workspace repo, official. Local dirs searched recursively to depth five. `amp.skills.disableClaudeCodeSkills` and `amp.skills.disableGlobalAgentsSkills` switch groups off. Symlinks and Windows: not stated. (https://ampcode.com/docs/customize/skills; https://ampcode.com/docs/customize/global-plugins-and-skills lists `~/.config/agents/skills` and `~/.config/amp/plugins`.)
- **Global agent instructions.** Personal: `$HOME/.config/amp/AGENTS.md` and `$HOME/.config/AGENTS.md`, both "always included if they exist"; system-wide: `/etc/ampcode/AGENTS.md`, `/Library/Application Support/ampcode/AGENTS.md`, `%ProgramData%\ampcode\AGENTS.md`. No order between the two personal files is stated. (https://ampcode.com/docs/customize/agents-md.)
- **User-level MCP server definitions.** `amp.mcpServers` in `~/.config/amp/settings.json` (or `.jsonc`); Windows `%USERPROFILE%\.config\amp\settings.json`; workspace `.amp/settings.json` (servers need `amp mcp approve`); `--mcp-config` flag highest; "Workspace beats user config". Settings: workspace overrides user; managed files `/Library/Application Support/ampcode/managed-settings.json`, `/etc/ampcode/managed-settings.json`, `%ProgramData%\ampcode\managed-settings.json`. (https://ampcode.com/docs/cli/settings; https://ampcode.com/docs/customize/mcp.) Local settings reload: not described. Remote definitions can also live on ampcode.com.
- **Auth state.** "Amp's secret storage" with automatic refresh; `amp mcp oauth logout <server>` clears. Location on disk: not stated.

## The shared `~/.agents/skills` convention

- The Agent Skills specification defines the contents of a skill directory (`SKILL.md` with `name`/`description` frontmatter, optional `scripts/`, `references/`, `assets/`) and says nothing about install locations (https://agentskills.io/specification).
- The client-implementation guide states: "The `.agents/skills/` paths have emerged as a widely-adopted convention for cross-client skill sharing. While the Agent Skills specification does not mandate where skill directories live…" It lists user-level `~/.agents/skills/` and project `<project>/.agents/skills/`, notes some clients also scan `.claude/skills/`, and says "project-level skills override user-level skills" is the universal collision convention. It does not say anything about symlinks. (https://agentskills.io/client-implementation/adding-skills-support.)
- Per agent (from the sections above): read `~/.agents/skills` — Codex, OpenCode, Pi, Gemini CLI, Copilot CLI, Cursor, Amp. Not documented as read — Claude Code.
- Machine check: `~/.agents/skills/` on this Mac contains `cua-driver` (a symlink into `~/.cua-driver/skills/`) and a real directory `use-railway`.

## Windows placement constraints

Everything here is about creating links; agent-side facts are in the per-agent sections.

- **Symbolic links need a privilege or Developer Mode.** `CreateSymbolicLinkW` flag `SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE` (0x2): "Specify this flag to allow creation of symbolic links when the process is not elevated. Developer Mode must first be enabled on the machine before this option will function." (https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createsymboliclinkw.) The underlying right is `SeCreateSymbolicLinkPrivilege` ("Create symbolic links"); "By default, members of the Administrators group have this right", and Microsoft advises against granting it to standard users. A restart is not needed, but a change applies at the account's next logon. (https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/create-symbolic-links.)
- **Developer Mode.** Turned on in Settings → System → Advanced → For developers (or the registry value `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\AppModelUnlock\AllowDevelopmentWithoutDevLicense = 1`). "Enabling Developer mode requires administrator access. If your device is owned by an organization, this option may be disabled." (https://learn.microsoft.com/en-us/windows/advanced-settings/developer-mode.) That page does not itself mention symlinks; the symlink link comes from the `CreateSymbolicLinkW` remark above.
- **File vs directory symlinks.** The API takes a directory flag (`SYMBOLIC_LINK_FLAG_DIRECTORY`, 0x1) at creation; `mklink` defaults to a file link and `/d` makes a directory link (https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/mklink). Removal uses `DeleteFile` for a file link and `RemoveDirectory` for a directory link (CreateSymbolicLinkW remarks).
- **Relative vs absolute symlinks.** A target with a device name is absolute, otherwise relative; "Relative symbolic links are restricted to a single volume"; symlinks can target a remote UNC path (https://learn.microsoft.com/en-us/windows/win32/fileio/creating-symbolic-links). Claude Code does not follow a `CLAUDE.md` or `.claude/rules` symlink to a UNC share (memory page above).
- **Junctions.** Directory-only; can link directories on different *local* volumes; "aren't permitted because they reference mapped network volumes, or they directly reference files". The Microsoft pages read don't state a privilege requirement for junctions (the hard-links-and-junctions page is silent; the privilege wording appears only in the symlink pages). `mklink /j` creates one. (https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions.)
- **Hard links.** Files only, same volume only (same page). Neither a hard link to a directory nor one across drives is possible.
- **Which agents' loaders see a junction as a directory.** No agent source or doc read here mentions junctions specifically. Behaviors observed: Pi and OpenCode call `stat`/`statSync` on entries (resolves through any reparse point the OS resolves transparently); Codex walks with `follow_directory_symlinks` — whether its Windows file-system walker treats a junction as a "directory symlink" was not tested; Claude Code docs only say "symlink". Not verified for any agent.
- **Same-user symlink evaluation.** The security-policy page mentions `fsutil behavior set symlinkevaluation` controlling which kinds of symlinks (local-to-remote etc.) are evaluated on a computer.
- **WSL.** Claude Code treats `\\wsl$` paths as local (not network) for the symlink rule above. Pi runs natively on Windows or inside WSL, with different shells (`docs/windows.md`). Each Windows/WSL pair has distinct home directories; no source read describes sharing config across them.
- **Where Windows config paths came from.** Only these Windows paths are stated in primary sources: Claude Code `%USERPROFILE%\.claude` (+ `.credentials.json`, managed `C:\Program Files\ClaudeCode\CLAUDE.md`), Codex system config `%ProgramData%\OpenAI\Codex\config.toml`, OpenCode `%ProgramData%\opencode`, Gemini `C:\ProgramData\gemini-cli\settings.json`, Amp `%USERPROFILE%\.config\amp\settings.json` and `%ProgramData%\ampcode\*`. All other Windows user paths above are the home-directory expansion of the macOS/Linux path in source code or are unstated.

## Open or conflicting facts

1. **Claude Code and `~/.agents/skills`.** Not listed in the skills docs part read (page truncated at 100k of 118k characters). Claude Code is the one candidate not documented as reading it. Untested here.
2. **Claude Code MCP token location.** Docs say "system keychain (macOS) or a credentials file" and give an exact path only for login credentials (`~/.claude/.credentials.json`). The MCP token store file/key is not documented in pages read.
3. **Claude Code `~/.claude.json` under `CLAUDE_CONFIG_DIR`.** The settings/claude-directory pages say `CLAUDE_CONFIG_DIR` moves `~/.claude` contents; whether `~/.claude.json` itself moves is not stated in what I read. Machine check: `~/.claude.json` is a sibling of `~/.claude/` and mixes `mcpServers` with caches, `oauthAccount`, and per-project state.
4. **Claude Code MCP hot edit.** Whether hand edits to `~/.claude.json`/`.mcp.json` apply without a restart: not stated on the MCP page.
5. **Codex symlinked `SKILL.md` files.** Docs and source cover symlinked skill *directories*; a comment in `discovery.rs` refers to "file symlinks omitted by the walk" with a probing fallback. Behavior for a symlinked file is not confirmed.
6. **Codex Windows admin skills path and Windows user paths.** Not documented; user home path is computed from `dirs::home_dir()`.
7. **Codex docs host moved.** developers.openai.com/codex/* returns 308 to learn.chatgpt.com; the older URLs in the Codex repo's `docs/*.md` stubs now redirect.
8. **OpenCode MCP auth path vs v2 source.** Docs say `~/.local/share/opencode/mcp-auth.json`; source at `df6fb9a46` (v2.1.4 line) has a credentials database for providers and I found no live code writing `mcp-auth.json`. Docs and code may describe different generations. Also the docs-vs-source Windows config dir: docs show `~/.config/opencode` only; code resolves to `%USERPROFILE%\.config\opencode` absent `XDG_CONFIG_HOME`.
9. **OpenCode's `AGENTS.md` docs vs `discovery.ts`.** The docs describe `~/.config/opencode/AGENTS.md`; the discovery source shows additional `.claude`, `.agents`, `.opencode` roots being walked for config. They are consistent for skills; instructions-file discovery was not traced through code.
10. **Gemini CLI symlinked skills.** Not stated in docs; loader uses `glob` with a single-level pattern and no `follow` option. Real behavior untested.
11. **Gemini CLI settings reload.** Skills and `GEMINI.md` have explicit reload commands (`/skills reload`, `/memory reload`); `mcpServers` edits in `settings.json`: no statement found.
12. **Copilot CLI.** Closed source. Skill precedence, MCP OAuth token location, and manual `mcp-config.json` reload are undocumented. The 1.0.66 changelog line about `COPILOT_HOME`/`--config-dir` and `~/.agents/skills` is ambiguous against the docs' list of personal locations.
13. **Cursor.** No file-based user-level instruction location, no stated precedence between global and project `mcp.json`, no stated symlink behavior or OAuth token location; hot reload undocumented ("update your local files and restart Cursor").
14. **Amp.** Symlinks, Windows skill paths, and the OAuth secret-store location are not stated. The two personal `AGENTS.md` paths have no stated ordering.
15. **Mixed-ownership files.** Confirmed (this Mac plus docs): Claude Code `~/.claude.json` (account, caches, per-project trust) and Codex `config.toml` (`[projects.*] trust_level`, `[tui]`) hold agent-written state in the same file as MCP definitions. Gemini `settings.json` and OpenCode `opencode.json` are general settings files that also hold the MCP key. Copilot's docs describe `mcp-config.json` as the definitions file, with app state in the separate `config.json` (changelog); Pi `mcp.json` and Cursor `mcp.json` are described as definitions files. Whether any of these rewrite their file on their own was only confirmed for Claude Code (rolling backups in `~/.claude/backups/` before rewrites).
16. **Skill `name` rules differ.** The agentskills spec requires the name to match the directory; Pi "neither requires nor warns"; OpenCode requires a match; Gemini/Claude/Codex name handling was not traced. (Pi `docs/skills.md`, OpenCode `skills.mdx`, agentskills.io spec.)
